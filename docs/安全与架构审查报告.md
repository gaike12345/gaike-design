### 1.2 认证与授权风险（P1）

| 编号 | 位置 | 问题描述 | 严重等级 |
|------|------|---------|---------|
| S-006 | `server/src/mank-core/auth/auth.service.ts:37` | **注册接口 UID 生成存在 TOCTOU 竞态**：使用 `generateNextUid()` 单独查 max(uid)，再 `prisma.user.create()`，两步非原子操作，并发注册可能产生 UID 冲突或跳号。ADR-004 要求使用 `createUserWithUid()`，但注册接口未遵循 | P1 |
| S-007 | `server/src/mank-common/utils/jwt.ts` | **JWT 无撤销机制**：Token 一旦签发，在过期前无法主动作废。用户修改密码、登出、被封禁后，原 Token 仍然有效 | P1 |
| S-008 | `server/src/mank-common/utils/jwt.ts:26` | **JWT 验证未指定算法**：`jwt.verify(token, SECRET)` 未指定 `algorithms: ['HS256']`，依赖库默认行为。虽然 jsonwebtoken v9+ 默认禁止 none 算法，但显式指定更安全 | P3 |
| S-009 | `server/src/mank-infra/middleware/auth.ts:77` | **超级管理员邮箱硬编码** `admin@manktv.com`，更换邮箱需修改代码发版，且攻击者知道目标邮箱 | P3 |

**建议：**
- 修复注册接口，改用 `createUserWithUid()` 保证原子性
- 引入 JWT 黑名单（Redis 存储），支持登出和密码修改后作废
- JWT 验证显式指定算法
- 超管邮箱可配置化，从环境变量或数据库读取

### 1.3 速率限制与 IP 伪造（P1）

| 编号 | 位置 | 问题描述 | 严重等级 |
|------|------|---------|---------|
| S-010 | `server/src/index.ts` + `rate-limit.ts:52` | **未配置 `trust proxy`，IP 可被伪造**：限流中间件从 `x-forwarded-for` 头取 IP，但 Express 未启用 `app.set('trust proxy', ...)`，攻击者可通过伪造 X-Forwarded-For 头绕过 IP 限流 | P1 |
| S-011 | `server/src/mank-infra/middleware/rate-limit.ts:90` | **AI 限流 `validate: false`**：关闭了 express-rate-limit 的默认验证，可能导致某些边缘情况未被正确限流 | P3 |

**建议：**
- 在 `index.ts` 中添加 `app.set('trust proxy', 1)`（或根据代理层数调整）
- 确保 Nginx 配置正确传递 `X-Forwarded-For`
- 评估 `validate: false` 的必要性，建议开启默认验证

### 1.4 文件上传安全（P2）

| 编号 | 位置 | 问题描述 | 严重等级 |
|------|------|---------|---------|
| S-012 | `server/src/mank-infra/middleware/upload.ts:80` | **允许上传 .pdf .txt .epub 等非图片文件，但无内容验证**：fileFilter 仅按扩展名白名单放行，魔数校验仅对图片类型执行。攻击者可上传包含恶意脚本的 .txt/.epub 文件（虽然直接下载风险较低，但结合其他漏洞可能被利用） | P2 |
| S-013 | `server/src/mank-infra/middleware/upload.ts:78` | **上传文件大小限制与 .env 不一致**：multer 硬编码 50MB，但 `.env` 中 `MAX_UPLOAD_SIZE=10485760`（10MB），配置项未生效 | P2 |
| S-014 | `server/src/index.ts:145` | **上传目录通过 Express 静态服务暴露**：`/uploads` 路径直接静态服务，若上传了 HTML/SVG 等可执行脚本可能导致 XSS（当前白名单无 html/svg，但 .svg 是标准图片格式且可含脚本） | P2 |

**建议：**
- 对所有上传文件进行内容类型验证，或限制为仅图片类型
- 统一上传大小限制，从环境变量读取 MAX_UPLOAD_SIZE
- SVG 文件需额外做 XSS 过滤（或禁止 SVG 上传）
- 上传文件使用独立域名提供访问，隔离主站 cookie

## 二、架构不一致问题

### 2.1 ADR 与实际代码不一致

| 编号 | ADR | 不一致点 | 影响 |
|------|-----|---------|------|
| A-001 | ADR-004 UID 账号体系 | **注册接口使用 `generateNextUid() + user.create()` 两步操作**，而非 ADR 规定的 `createUserWithUid()` 原子操作。`auth.service.ts:37` 调用 `generateNextUid()` 获取 UID 后单独创建用户，存在 TOCTOU 竞态风险 | 并发注册时可能 UID 冲突，导致注册失败 |
| A-002 | ADR-001 超级管理员不变量 | **ADR 规定"启动纠偏：服务启动/seed 时校验 superadmin 唯一性"**，但实际代码中 seed.ts 是手动执行的脚本，服务启动时（`index.ts`）没有自动纠偏逻辑 | 若数据库被手动修改出现多个 superadmin，服务不会自动修复 |
| A-003 | ADR-002 额度原子预扣 | **文档引用路径为 `lib/generation.ts`**，实际代码路径为 `mank-core/billing/tokenService.ts` 和 `mank-infra/middleware/generation.ts` | 文档维护问题，不影响功能 |
| A-004 | ADR-003 双审核 | **文档引用路径为 `lib/moderation.ts`、`lib/llmRoute.ts`**，实际路径为 `mank-core/moderation/moderation.ts`、`mank-core/llm/llmRoute.ts` | 文档维护问题，不影响功能 |
| A-005 | ADR-004 UID 账号体系 | **文档引用路径为 `lib/uidGenerator.ts`**，实际路径为 `mank-core/auth/uidGenerator.ts` | 文档维护问题，不影响功能 |

## 三、部署风险

### 3.1 Docker 部署安全

| 编号 | 位置 | 问题描述 | 严重等级 |
|------|------|---------|---------|
| D-001 | `server/Dockerfile` + `web/Dockerfile` | **容器以 root 用户运行**：Dockerfile 未创建非 root 用户，Node/Nginx 进程以 root 权限执行，容器被攻破后直接获得 root 权限 | P1 |
| D-002 | `docker-compose.yml:62,123,152` | **端口过度暴露**：后端 3000、PostgreSQL 5432、Redis 6379 均直接映射到宿主机。生产环境应仅暴露 Nginx 的 80/443，数据库和缓存不应公网可达 | P0 |
| D-003 | `docker-compose.yml:38` | **JWT_SECRET 默认值弱**：默认值 `please-change-this-to-a-long-random-string`，用户未配置时直接使用弱密钥 | P0 |
| D-004 | `docker-compose.yml:119` | **PostgreSQL 默认密码弱**：默认值 `change-me-in-production`，极易被爆破 | P0 |
| D-005 | `docker-compose.yml:148` | **Redis 无密码**：Redis 实例无认证且端口映射到公网，可被未授权访问和数据篡改 | P1 |
| D-006 | `docker-compose.yml` | **缺少安全加固配置**：无 `security_opt`、`cap_drop`、`read_only: true`、`pids_limit` 等安全限制 | P2 |
| D-007 | `docker-compose.yml:57` | **IMAGE_SIGNING_SECRET 默认值可预测**：`img-sign-key-change-in-prod`，攻击者可伪造图片签名 | P2 |

**建议：**
- Dockerfile 中添加非 root 用户（如 `node` 用户）
- 生产环境移除 PostgreSQL、Redis、后端服务的端口映射，仅通过内部网络通信
- 强制要求配置强密码和密钥，移除不安全的默认值
- Redis 添加密码认证（`--requirepass`）
- 添加 `cap_drop: - ALL`、`read_only: true` 等安全配置

## 六、总体评价

**安全基线：中等偏上**

项目在安全架构设计上比较完善，有完整的 ADR 体系、安全加固文档、分层中间件设计、原子额度扣减、双审核机制、结构化日志脱敏等优秀实践。核心安全逻辑（JWT 认证、RBAC、速率限制、文件上传校验、内容审核）基本到位。

**主要问题集中在三个方面：**

1. **配置安全**：默认值弱、真实密钥在开发环境中暴露、Docker 端口暴露过多
2. **部署安全**：容器以 root 运行、PM2 以 root 运行、备份明文存储、无回滚机制
3. **文档与代码一致性**：部分 ADR 路径引用过时，注册接口未使用推荐的原子 UID 生成方式

建议优先处理 P0/P1 级别问题，特别是密钥轮换和 Docker 网络安全加固。
